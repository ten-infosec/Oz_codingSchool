## 3. 파일별 역할

### 3-1. `app/main.py` (담당: 엄태은)

**역할**: 서버가 처음 켜질 때 실행되는 시작점이다. 들어온 요청을 알맞은 API로 보내 주는 정문(안내 데스크) 역할을 한다.

**하는 일**

| 순서 | 코드 | 설명 |
|---|---|---|
| 1 | `app = FastAPI()` | FastAPI 앱(서버 본체)을 만든다 |
| 2 | `BASE_DIR = Path(__file__).resolve().parent.parent` | 프로젝트 최상위 폴더 경로를 구한다 (`app/main.py` → `app` → 프로젝트 폴더) |
| 3 | `os.mkdir(BASE_DIR / "static")`, `"media"` | `static`, `media` 폴더가 없으면 새로 만든다 |
| 4 | `app.mount("/static", ...)` | `/static` 주소로 들어오면 `static` 폴더의 파일(CSS, JS, index.html)을 그대로 내준다 |
| 5 | `app.mount("/media", ...)` | `/media` 주소로 들어오면 사용자가 업로드한 파일(예: X-ray 이미지)을 내준다 |
| 6 | `GET /healthcheck` | 서버가 살아 있는지 확인하는 주소. `{"status": "ok"}`를 돌려준다 |
| 7 | `GET /` | 첫 화면으로 `static/index.html`을 보여 준다 |
| 8 | `GET /{path:path}` (`catch_all`) | 위에서 처리되지 않은 **모든 주소**를 받아 `index.html`을 보여 준다. 단 `api/v1`, `static/`, `media/`로 시작하는 주소는 404를 돌려준다 |

- `include_in_schema=False`: Swagger(`/docs`)에 표시하지 않는다. API가 아니라 서버 운영용 주소이기 때문이다.

**주의할 점: 라우터 등록 위치**

- 새로 만든 API 라우터는 `app = FastAPI()` 바로 아래에서 `app.include_router(라우터)`로 등록한다.
- FastAPI는 **위에서부터 순서대로** 주소를 비교한다. `catch_all`의 `/{path:path}`는 모든 주소와 일치하므로, 라우터를 catch_all **아래**에 등록하면 요청을 catch_all이 먼저 가져가 API가 동작하지 않는다.
- 그래서 라우터 등록은 반드시 catch_all보다 **위**에 둔다.

```python
from app.apis.practice_apis import router as practice_router

app = FastAPI()

# catch_all보다 위에 등록
app.include_router(practice_router)
```

## 6. API 구현 흐름 (담당: 엄태은)

2일차 연습 API(`practice_apis.py`)는 데이터, 검사, 로직, 주소 연결을 **한 파일**에 모두 작성했다.
템플릿은 이것을 **역할별 폴더로 나누어** 작성하도록 구성되어 있다.

### 6-1. 새 API를 만드는 순서 (예: 환자 등록 API)

| 순서 | 파일 | 하는 일 |
|---|---|---|
| 1 | `app/models/patient.py` | DB 테이블 구조를 정의한다 (SQLAlchemy 모델) |
| 2 | `app/schemas/patient.py` | 요청·응답 데이터 형식을 정의한다 (Pydantic 모델) |
| 3 | `app/repositories/patient.py` | DB에 저장·조회·수정·삭제하는 코드만 담당한다 |
| 4 | `app/services/patient.py` | 업무 규칙을 처리한다 (예: 중복 환자 확인 후 등록, 없으면 404) |
| 5 | `app/apis/patient.py` | URL과 HTTP 메서드를 연결한다 (`@router.post(...)`) |
| 6 | `app/main.py` | `app.include_router(...)`로 라우터를 등록한다 |

- DB 모델을 새로 만들거나 바꾸면 Alembic 마이그레이션(`uv run alembic revision --autogenerate`, `uv run alembic upgrade head`)으로 실제 DB에 반영한다.

### 6-2. 요청이 처리되는 방향

```
요청 → main.py → apis → services → repositories → DB
응답 ← main.py ← apis ← services ← repositories ← DB
```

- `apis`는 요청을 받고 `schemas`로 데이터를 검사한다.
- `services`는 규칙을 판단하고, DB 작업이 필요하면 `repositories`를 부른다.
- `repositories`는 `models`를 이용해 DB와 직접 대화한다.

### 6-3. 2일차 연습 코드와 비교

| 2일차 `practice_apis.py` | 템플릿 구조 |
|---|---|
| `user_list` (메모리 임시 데이터) | `models/` + 실제 DB |
| `UserCreate`, `UserUpdate` (BaseModel) | `schemas/` |
| `user_list.append(...)`, 리스트에서 찾기 | `repositories/` |
| 이메일 중복 검사, 404 처리 | `services/` |
| `@router.post("/users")` 등 | `apis/` |
| `app.include_router(practice_router)` | `main.py` |

### 6-4. 이렇게 나누는 이유

- **한 파일이 하나의 역할만** 맡아서 코드를 찾고 고치기 쉽다.
- DB를 바꾸더라도 `repositories`만 고치면 되고 `apis`, `services`는 그대로 둘 수 있다 (결합도 낮추기).
- 팀원들이 서로 다른 파일을 맡아 동시에 작업해도 충돌이 적다.
